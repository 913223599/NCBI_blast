# 注释流程"库存在但未连接"问题诊断与修复报告

> 复现样本：`C:\Users\Administrator\Desktop\025cl.fasta`（ngcs_scaffold_1，58,389 bp，GC 46.38%）
> 诊断环境：Windows，项目 `D:\NCBI blast`，BLAST+ 2.17.0+，未安装 WSL 发行版
> 结论：**注释流水线本身没问题，是"数据库路径解析 / 注册表 / 引擎调度"三处连接断掉了**，导致 PhageScope、Swiss-Prot、CDD、VFDB、CARD、Pharokka、Phold 全部被静默跳过，最终只剩内置引擎在跑。

---

## 1. 现象

| 观测点 | 修复前 | 说明 |
|---|---|---|
| 同一样本 `025cl.fasta` 注释结果 | **annotated 0 / 108 CDS** | 全部落到 hypothetical protein |
| 历史样本 T5-E1 注释结果 | 19 / 168（11%） | `results/annotations/ANNO_DEFB6310/summary.json`，`engine_contributions` 只有 `{"Builtin": 168}` |
| 设置 → 本地数据库 | PhageScope / Pharokka / Phold 全部"❌ 尚未部署"，且只列出 3 个库 | 实际磁盘上有 8 个库、约 58 GB |
| 注释控制台 | 无任何报错，直接"注释全部完成" | 阶段 2/3/4 失败被 `logger.warning` 吞掉 |

`025cl.fasta` 的 CDS 数（108）与 coding density（92.9%）本身合理，问题完全在功能赋名环节。

---

## 2. 根因（按影响排序）

### R1. 数据库被多套了一层目录：真实数据在 `database/database/`，代码只读 `database/`

```
D:\NCBI blast\database\                 <- ToolConfig.DATABASE_ROOT（代码读这里）
├─ phagescope\        0 个文件          <- 空
├─ pharokka_db\       0 个文件          <- 空
├─ phold_db\          0 个文件          <- 空
├─ 16S\  taxonomy\                      <- 这两个有数据
└─ database\                            <- 真正的库全在这里
   ├─ phagescope\      973 MB（含 phagescope_proteins.psq + metadata）
   ├─ swissprot\       691 MB（swissprot.psq）
   ├─ cdd_pfam\      41.6 GB（cdd_pfam.pal + 分区 .rps）
   ├─ vfdb\  card\  pharokka_db\  phold_db\  defense_finder\  checkv_db\ ...
```

`ToolConfig.DATABASE_ROOT = PROJECT_ROOT / "database"`，而所有库目录在其下一层，于是 `installed` 判定全部为 False，`FunctionalAssigner` 也找不到 `phagescope_proteins.p*` 索引。

**这是"库存在但未连接"的直接原因。**

### R2. 注册表漂移：`database/registry.json` 缺 5 个库

主注册表只有 `silva / ncbi_16s / rdp / phagescope / pharokka / phold` 6 条；`database/database/registry.json` 有 11 条（多出 `swissprot / cdd_pfam / defense_finder / vfdb / card`）。`BioDbManager` 按注册表实例化，所以**界面上连这些库的条目都没有**，更谈不上状态与部署。

### R3. 用运行目录（CWD）推导数据库根

`FunctionalAssigner`、`DeepSafetyAuditor` 原来是 `Path(os.getcwd()) / "database"`。用不同方式启动（IDE、脚本、批处理）就会指向 `database/database`，与 R1 叠加后行为随机。

### R4. 全部外部引擎都经 WSL 调度，而本机没有 WSL 发行版

`PharokkaEngine / PholdEngine / ProdigalEngine / ProkkaEngine` 的 `is_available()` 都是 `wsl -d Ubuntu -u root which <tool>`。当前机器 `wsl -l` 无任何发行版 → 永远返回不可用。数据库文件明明在，却因为"运行时"缺失而被判为"未部署/不可用"。

### R5. 硬编码路径没跟着项目迁移

- `pharokka_engine`：`-d /opt/pharokka_db`
- `phold_engine`：`-d /opt/phold_db`，并硬编码 `ln -sfT '/mnt/f/NCBI blast' /tmp/ncbi_blast_tmp`
- `scripts/setup_*.sh`：注释仍写"F 盘外挂传送门"

项目已从 `F:\NCBI blast` 迁到 `D:\NCBI blast`，这些路径全部失效。

### R6. BLAST+ 解析依赖 PATH，配置里的版本号是错的

`config.json` 里 `blast_bin_path = C:\Program Files\NCBI\blast-2.16.0+\bin`（不存在），实际安装为 `2.17.0+`。原代码 `shutil.which("blastp")` 只是碰运气命中 PATH。

### R7. 静默降级：失败不可见

`pipeline.execute` 阶段 2/3/4 都是 `try: ... except Exception: logger.warning(...)`，任务仍然以 `completed` 收尾、进度条 100%。用户只看到"注释率低"，看不到"哪个库没连上、为什么跳过"。

## 5. 仍需你确认 / 处理的三件事

1. **重启桌面端**：Python 侧改动需要重启应用（`web-next` 窗口）才会生效；`results/` 里旧任务的 `summary.json` 没有诊断字段，重跑一次即可看到新的逐阶段日志。
2. **Pharokka / Phold 是否要启用**：它们的库（1.8 GB / 13.3 GB）已就绪，但需要 WSL + Ubuntu（Phold 还建议 GPU）。若要用，需要先 `wsl --install -d Ubuntu`，再跑 `scripts/setup_pharokka.sh`；不装也不影响主流程——PhageScope/Swiss-Prot/CDD 这条纯 Windows 链路已经是主力。Prokka/Prodigal 同理。
3. **磁盘整理（可选，约 33 GB）**：
   - `database/database/16S/`、`database/database/taxonomy/` 与 `database/16S/`、`database/taxonomy/` 完全重复（嵌套份多一个 `.tmp`），可删嵌套份；
   - `database/database/chunk_01..09.msh` 共 **29 GB**，是早期 PhageScope mash 草图残留，代码中无任何引用，可删；
   - 若希望目录彻底"归位"，可把 `database/database/<库>` 直接移动到 `database/<库>`（同一分区为秒级重命名）。代码已做双目录兼容，移动与不移动都能正常连接，所以这一步不着急。
